# NOTES — decisions the design did not determine

The design (`design.json`) has eight process expressions and nothing else: no goal, no system or process descriptions,
no representation descriptions, no references, no images. Identifiers are opaque (`r1`…`r29`). So nearly everything
beyond the *shape* of the processes (actors, operations, roles, media, collections, loops, connections) is my choice.

## 1. Interpretation of the whole system

| Design element | What it fixes | What I chose |
| --- | --- | --- |
| Overall purpose | Starts from a table (`r1 tabular`), ends in visuals, uses spatial segments and labels | A **data-driven pictorial chart maker**: table → model-drawn illustration → segmented objects bound to data → per-category redraws → pictorial charts → annotated export. |
| r2 record | "artifact record" extracted from the table | Column profile: type (number/category/text), distinct count, category values, min/max/mean/sum, default category & value field. |
| r3 language | translated from r2 | A plain-prose data description built from a template. |
| r4 language | generated by model_1 | A numbered brainstorm of six visual concepts. |
| r5 language* | extracted from r4 | Concept lines parsed by regex (numbered or bulleted). |
| r6 visual | translated by tool_1 in the state with r5 | A plain SVG bar chart of the default value per category ("data shape"). |
| r7 instruction* | composed from r5 + r6 | One illustration prompt per concept (max 4, user chooses 2–4), embedding the bar heights as text so the picture echoes the data. |
| r8 visual* | model_2 generate | SVG illustrations (no image model is available). |
| r9 / r10 | human specify / compose | A free-text "direction"; r10 = direction + all r5 concepts + r6 shape. Each round generates 1–4 images from the same r10. |
| r11 | human select | The chosen SVG, with every shape tagged `data-eid` so it can be segmented. |
| r12 selection spatial* | human select on r11 | Rectangles dragged over the illustration. |
| r13 artifact spatial* | model_3 extract, then human modify | Segments = named sets of SVG element ids + bounding box. model_3 is a text LLM that receives the geometry (id, tag, group, fill, bbox) of shapes overlapping the rectangles — an LLM substitute for a segmentation model. |
| r14 label record* | human assign | `{segmentId, role: mark/anchor/decoration, field}`. I added the "anchor" role (position only) so several objects can serve as layout slots while only one is redrawn. |
| r15 / r16 | tool_2 extract | r15 = SVG crop (all non-segment shapes removed, viewBox fitted); r16 = the segment bbox. |
| r17 | model_4 generate | 1–2 sentence style description of the crop (shapes, hex colours, proportions). |
| r18 / r19 | compose / model_5 generate | One prompt per category value of the bound field (max 10); model_5 draws a sibling icon in SVG with the crop's aspect ratio. |
| r20 spatial* | tool_3 extract | Anchor slots: bboxes of mark/anchor segments sorted left to right. |
| r21 instruction record | human specify | Chart spec: element set, value field, aggregate (sum/mean/count), sort, value per icon, icon size range, layouts. |
| r22 visual* | tool_3 translate | One mark per category: the category's variant + aggregated value. |
| r23 visual* | tool_3 compose | One chart per chosen layout: *in place* (marks at the original object positions, sized by value), *isotype rows* (one icon per unit, partial last icon clipped), *sized row* (area ∝ value), *icon columns*. |
| r24 instruction record | human specify | A highlight query `{field, op, value}` with ops `max, min, =, !=, >, <, >=, <=, contains`. |
| r25 artifact record | tool_4 match | Matching row indices and the chart categories they fall in. |
| r26 instruction record | human select | Chart choice, categories to annotate (pre-ticked with all matches), title, subtitle, note. |
| r27 visual | tool_3 compose | Final SVG with title block, callout boxes and labels on the annotated categories. |
| r28 categorical | human specify | Export format: SVG, PNG (3×), JPEG (3×). |
| r29 visual | tool_3 translate | The downloaded file. |

## 2. Process flow and triggers

- One application, a left-hand stepper with seven screens: Data, Illustrate (P1 output + P2 + P3), Segment & bind (P4),
  Element variants (P5), Chart (P6), Annotate (P7), Export (P8). Later steps unlock when their inputs exist.
- P1 runs as one automatic chain triggered by the "Brainstorm & illustrate" button (no human step inside P1).
- P5 runs as one automatic chain (crop → describe → compose → draw) on a button; its loop is per-variant Regenerate.
- The P6 and P7 loops (human modify → back to the spec) are implemented as live recomputation: every edit of r21/r26
  recomposes immediately, since those steps are deterministic tools.
- Loading a new table resets the session; choosing a new illustration resets everything downstream of r11.
- Earlier versions are kept where the design versions or loops them: every r8 round is a tab; each variant keeps up to
  five earlier outputs that can be restored.
- The design's connection "process 1 continues from process 6/7 through r1" is treated as shared state (the table is
  available throughout), not as a loop back to P1.

## 3. Model calls

- Provider: Claude Code CLI via `callModel()` (`server/model.ts`): `claude -p --output-format json --model <m> --tools ""
  --system-prompt <s>`, prompt on stdin, `CLAUDECODE` removed. Concurrency limit 4, timeout 240 s.
- Models: `haiku` for text/JSON (model_1, model_3, model_4), `sonnet` for SVG drawing (model_2, model_5). Overridable.
- Each model role has its own system prompt and prompt builder (`server/prompts.ts`).
- Validation of `~` outputs: SVG is extracted from the reply, scripts/event handlers/foreignObject/external hrefs are
  stripped, a viewBox is enforced, and at least one shape is required; one automatic retry on validation failure.
  Segmentation JSON is parsed leniently, unknown or duplicate element ids are dropped, and empty segments discarded.
- Loading states per item (spinners), per-item errors with Retry, and regeneration everywhere a model draws.
- SVG constraints in prompts: fixed 400×300 viewBox, one `<g id=…>` per object, no text/images/filters, ≤150 shapes
  (illustrations) or ≤60 (icons).

## 4. Stack, layout, styling

- Vite + React 19 + TypeScript frontend, no UI library, plain CSS; Express backend run with `tsx`.
- State: one React state object, persisted to `localStorage` (in-flight generations are marked "interrupted" on reload).
- Styling: warm off-white background, dark sidebar, orange accent (#d9480f), cards with rounded corners. Each panel shows
  its design identifier as a small tag (e.g. `r21 · instruction record`) for traceability.
- Segmentation UI: transparent SVG overlay with the illustration's viewBox for drawing boxes; in edit mode the active
  segment's shapes stay opaque and others are dimmed; coloured dashed boxes label each segment.
- CSV parsing is hand-written (comma, tab, semicolon; quoted fields; numeric coercion). Two sample datasets are bundled.
- Tests: Vitest + happy-dom for all tool steps (14 tests); `scripts/e2e.mjs` (Playwright) drives all eight processes with
  real model calls and saves screenshots to `e2e-shots/`. Last run: all processes completed and a PNG was exported.

## 5. Known limitations

- The model_3 "segmentation" works only because illustrations are SVG with separable shapes; it would need a real
  segmentation model for raster images.
- Variant quality depends on the model; a variant can come back off-category (e.g. a red "pear"), which is why each
  prompt is editable and regenerable.
- The in-place layout puts categories beyond the number of anchors on an extra row at the bottom.

## 6. Did the design remind me of a published system?

Yes, loosely. The overall shape — data → model-generated imagery → user-selected image → segmentation of objects (a
model extracting regions from user-drawn selections) → binding objects to data → generating per-category element
variants → composing a data-driven pictorial chart — resembles recent research systems for **AI-assisted pictorial
visualization / infographic authoring**, in particular **ChartSpark** (Xiao et al., IEEE VIS 2023, text-to-image
generation of semantic context embedded in charts) and data-driven pictograph/isotype authoring tools in the line of
**DataQuilt** (Zhang et al., IUI 2020, extracting graphical elements from reference images and binding them to data)
and **Infomages**/**DataSelfie**-style work. The `[model_3 extract]` from `selection spatial` strongly suggests a
promptable segmenter such as SAM. I am not certain which specific system the design encodes.

Choices that came from that background knowledge rather than from the design:

- Treating r1→r8 as "brainstorm themes, then generate illustrations" and r6 as a chart of the data that conditions the
  image prompts (ChartSpark-like conditioning on the data shape).
- Reading P4 as "box prompts → segmentation → mask refinement → bind elements to data fields" (SAM-style prompting,
  DataQuilt-style binding), and the r14 roles mark/anchor/decoration.
- Reading P5 as "crop the element, caption it, and generate per-category variants of it" for use as glyphs.
- The concrete layouts in P6 (isotype rows with a "1 icon = N" key and partial icons, area-scaled glyphs, in-place
  glyphs at the original object positions) come from general pictorial-chart / ISOTYPE conventions.
- Reading P7 as "query the data, pick matches, annotate the chart" and P8 as format export.

The use of SVG for every visual, the Claude-only segmentation via element geometry, the UI layout, and all prompts are my
own choices driven by the constraint that only the Claude Code CLI was available.
